description: Apply an explicit release and preserve enough evidence to resume it.

## Prepare the target

Run `kello login`, then `kello link --project-id <id> --branch <branch-id>`. Kello reuses the official Neon login and discovers the database and migration owner. A linked unprotected, nondefault branch is the default preview target. Production requires an explicit target in optional `kello.config.ts`. CI can supply `NEON_API_KEY` instead of an interactive login.

Use `kello provision --branch <declaration.json> --dry-run --json` to inspect branch infrastructure creation; omit `--dry-run` to apply or resume. A declaration contains target identifiers and environment-variable names, not raw secrets. Provisioning and release deployment are separate steps.

## Deploy from project configuration

Normal linked projects need no `kello.config.ts`. Run `kello generate`, generate and review a migration with `kello migrations generate --name initial`, then run `kello deploy --dry-run --json` and `kello deploy --json`. The CLI creates its restricted runtime role, resolves its credentials through Neon, applies eligible migrations, provisions declared private buckets, deploys service and worker functions, binds triggers and activates the verified runtime.

Kello stores a random activation secret per project, branch, deployment and release in owner-only Postgres metadata. Runtime roles cannot read that table. Link files, generated client configuration and `.loom` receipts contain no credentials. Keep `.loom` receipts for recovery; retries retrieve the same secret from Postgres. Existing roles not created by this managed flow require explicit credential overrides, as do custom environment-source names.

Install `vite-plus` in the application’s devDependencies to build Node 24 deployment archives. For declared live functions, inspect `kello realtime status` and explicitly enable the selected branch with `kello realtime enable --origin <frontend-origin>`. Deployment refuses missing or pending Realtime readiness for those functions. Signing secrets use the protected deployment channel; generated clients receive only public coordinates.

## Review an explicit release

Prepare committed migration artifacts and obtain the exact source version from `kello doctor --json`. The release declaration binds that version, release key, target, database roles, service and worker identities, activation-token source and reviewed compatibility range. It is immutable input to a resumable operation, not a mutable deployment checklist.

```sh
kello deploy --release releases/preview.json --dry-run --json
kello deploy --release releases/preview.json --json
```

Dry-run resolves and reads the target, including database history, live drift, compatibility and saved receipts, without applying release changes. It still needs credentials and network access. Apply rechecks the target and records acknowledged stages so the same declaration can resume after failure.

The compatibility range must come from application evidence. A structurally valid schema does not prove that every old query or writer remains compatible.

The strict release declaration accepts these required fields:

| Field                                          | Value                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `format`                                       | `1`.                                                                                             |
| `releaseKey`                                   | A unique 64-character lowercase hexadecimal key, stable across retries.                          |
| `deployment`, `version`                        | Logical deployment name and the exact source version.                                            |
| `environment`                                  | `preview` or `production`, resolving the configured target.                                      |
| `databaseName`, `migrationRole`, `runtimeRole` | Existing database and role names.                                                                |
| `quarantine`                                   | `clone` for a new preview clone; `preserve` for an existing branch or production.                |
| `migrationHashes`                              | All committed migration plan hashes in application order.                                        |
| `reviewedHashes`                               | Explicitly reviewed unsafe or custom migration hashes.                                           |
| `schema`                                       | Reviewed `minimum`, `maximum`, and `target` schema hashes, with migration anchors when required. |
| `slugs`                                        | Distinct `service` and `worker` names of 1–20 lowercase letters or digits.                       |
| `activationTokenEnv`                           | Local variable containing the 64-character lowercase hexadecimal activation secret.              |
| `variables`                                    | Map from deployed variable names to local environment-variable names.                            |

Include the configured runtime database URL in `variables`, for example `"LOOM_DATABASE_URL": "PREVIEW_RUNTIME_URL"`. Do not map migration credentials, the provider API key or activation token as application variables. Unknown fields and raw secret fields are rejected.

## Retry and rollback

After interruption, retain the declaration, token values, migration artifacts and saved release evidence. Retry the same declaration to resume; changing inputs under the same release key conflicts with the recorded operation.

To restore retained code, use a new release key and the earlier completed release's `retainedReleaseKey`, preserve quarantine state, and restore its exact source and runtime inputs. Keep current migration artifacts and declare a reviewed range covering the current database. Rollback does not reverse migrations or delete expanded data.

## Retire database authority

`kello retire database --retirement <file> --json` performs the database retirement stage for a completed release. It checks release identity, ingress handoff, compatible runtime health, pending jobs and live client-session dependencies before retiring its activation grant.

This stage retains provider resources and historical artifacts. It does not stop all remote processes, drain external action side effects or delete old functions. Do not treat a database retirement receipt as proof of complete provider cleanup.

## Confirm the release serves your application

Check the CLI's completed release receipt, then call an authenticated finite procedure against the returned service URL. Exercise a mutation and observe it from a live subscription. If your app uses jobs or uploads, run one real job or finalized upload through the deployed worker and trigger path.

If activation or verification fails, retain the receipt and retry with the same release inputs. Point the frontend at the service URL after verification succeeds.
