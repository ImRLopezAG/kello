SSR is optional. Client-only apps need only the browser provider. For private server prefetch, the incoming frontend request must actually carry a usable credential. A cookie set on a separate Kello service origin is not automatically available to Next.js or Start.

## One client and cache per request

```ts
import { withKelloServerSession } from "kello/client";
import { createServerClient } from "../kello/_generated/api";

const result = await withKelloServerSession(
  createServerClient,
  { url: serviceUrl, getToken: async () => requestToken, signal: request.signal },
  async ({ connection, queryClient, dehydrate }) => {
    const greeting = await queryClient.query(connection.rpc.tasks.greeting.queryOptions({ input: { name: "Ada" } }));
    return { greeting, hydration: dehydrate() };
  },
);
```

`requestToken` comes from the incoming request or a provider-supported server API; it is not a shared module value. The helper returns `null` when no token exists, verifies supplied credentials, and disposes the connection/cache after work finishes or is aborted. Errors propagate to your framework boundary.

Pass the resulting `hydration` only to the matching browser provider. It contains a verified session descriptor and encoded query state, not the bearer token. Private HTML must not enter a shared cache.

## Finite and live data

Do not issue a Neon subscription in a server loader. Prefetch a finite endpoint when you need server HTML. On the client, subscribe once to the declared live query. Live capabilities and rows stay outside ordinary Query hydration; a finite SSR result does not certify live transaction progress.

The examples render finite SSR notes as fallback content and start one live subscription in the browser. They do not run an additional finite notes hook there. The root routes demonstrate this optional path; `/client` disables the private UI's SSR entirely.

## Framework adapters are optional

`kello/next/server` and `kello/start/server` also export managed-Neon frontend proxy adapters for applications that explicitly choose that topology. They are not prerequisites for Kello authentication. The current framework examples use Kello-hosted auth plus a small request-token adapter instead.

Never serialize a provider token, private signing secret, or provider SDK instance into route data. Authorization still runs on the Kello server after hydration; cached data does not grant authority.

## Connection helpers

The manual connection helper returns native options; its caller owns disposal. The SSR helper owns disposal automatically.
