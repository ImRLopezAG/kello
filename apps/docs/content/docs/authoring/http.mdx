## REST procedures and custom routes

Public oRPC contracts can generate a REST graph when `openapi: true` is enabled in `kello.config.ts`. Declare native oRPC routing metadata and supported schemas. Kello's HTTP adapter uses Hono and the native oRPC handlers.

Components can instead declare native request/response handlers, useful for callbacks and signed webhooks. Their routes mount under `/api/components/<mount-path>`. Reserved Kello auth, storage, and RPC routes retain their own checks.

## Component route contract

A `ComponentHttpRoute` declares `method`, `path`, and `access`, then either `handle` or an oRPC `router`. Handlers receive the original request, cancellation signal, verified session when applicable, and scoped component context.

| Access kind      | Required behavior                                                              |
| ---------------- | ------------------------------------------------------------------------------ |
| `verified-user`  | Verify a session, then run the route's `authorize(session, request)` predicate |
| `signed-webhook` | Verify the original bounded byte body before parsing or performing writes      |
| `anonymous`      | Explicitly allow unauthenticated ingress; still validate all input             |

Routes may configure `origins`, `maxRequestBytes`, and `requestTimeoutMs`. Defaults are 1 MiB and 30 seconds; supported maxima are 10 MiB and 120 seconds. CORS controls browser access; it is not webhook authentication or record authorization.

## Webhook processing

Verify the provider signature over the exact body bytes supplied to the verifier. Do not parse and reserialize JSON before verification. Apply the provider's timestamp/replay rules and keep signing secrets in the component environment. Only acknowledge successful durable acceptance; use a stable event ID to deduplicate provider redeliveries.

If a webhook synchronizes users into local tables, that synchronization is an application decision. Installing a provider SDK alone does not require copying its data or creating webhook routes. See [SDK services](/authoring/sdk-services).

Better Auth owns its native plugin endpoints through its mounted handler; do not translate every plugin route into an oRPC procedure. See [Better Auth](/authoring/better-auth).

Create `kello/components/health/setup.ts`:

The generated `setup` import binds the component to its own context. Run `kello generate` after adding the file to create that facade.

Import it into `kello/app.config.ts` and call `app.use(health)`. After publishing, request `GET <KELLO_SERVICE_URL>/api/components/health/ready`; expect `{ "ok": true }`. This confirms the route is serving, not database readiness or authentication health. The endpoint intentionally returns no private data.

For a webhook, replace anonymous access with `signed-webhook` and the provider's signature verifier. Keep route registration, signature verification, payload validation, and durable processing distinct. An invalid signature should fail before your handler writes anything; a duplicate valid event should not duplicate its effect.
