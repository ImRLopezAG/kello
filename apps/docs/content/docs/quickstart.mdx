## Build the local package

Use the repository's pinned Bun toolchain and Node 24. From the repository root:

```sh
bun install --frozen-lockfile
bunx turbo run build --filter=kello-cli
```

The examples consume the built `kello` runtime through public subpath imports such as `kello/server` and `kello/react/neon`. Their `kello-cli` development dependency provides the `kello` executable and configuration APIs. For an application outside this workspace, install matching runtime and CLI release versions with `bun add kello` and `bun add --dev kello-cli vite-plus`.

## Choose an example

| Directory                        | Client behavior                                                                    |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `packages/examples/next`         | `/client`: client-only live query; `/`: optional bearer-authenticated SSR          |
| `packages/examples/start`        | `/client`: client-only Suspense live query; `/`: optional bearer-authenticated SSR |
| `packages/examples/tasks`        | React/Vite tasks and optimistic updates                                            |
| `packages/examples/jobs-storage` | Private uploads and durable processing                                             |
| `packages/examples/components`   | Mounted component APIs and services                                                |

Each example owns its backend. Link separate disposable branches so their schemas and deployment identities do not conflict.

## Authenticate and link

From the selected example directory:

```sh
bunx --no-install kello login
bunx --no-install kello link --project-id YOUR_PROJECT_ID --branch YOUR_BRANCH_ID
bunx --no-install kello doctor --json
```

Kello uses the official Neon credential profile and discovers the database and migration owner. Choose an unprotected, nondefault development branch. CI can use `NEON_API_KEY`; do not put provider credentials in browser variables. A normal linked project does not need `kello.config.ts`. Examples may retain namespace overrides.

Copy the example's `.env.example` to `.env` and configure its application values. Managed Neon auth also requires branch auth setup and the correct allowed frontend origin. Backend auth secrets belong on the Kello service, never in a `NEXT_PUBLIC_*` or `VITE_*` variable.

## Generate and review the database

```sh
bun run generate
bunx --no-install kello schema diff
bunx --no-install kello migrations generate --name initial
bunx --no-install kello migrations status
```

If the example already has a migration history, retain it and inspect the diff instead of creating a second initial migration. Commit reviewed history under `kello/_generated/migrations`. Generation alone does not apply SQL or deploy functions.

## Deploy and connect

```sh
bunx --no-install kello deploy --dry-run --json
bun run deploy
```

The linked deployment flow prepares the restricted runtime role, applies eligible migrations, deploys the service and worker, and activates the verified runtime. Changes requiring review must be explicitly approved by migration hash; do not bypass a rejected migration.

For Next.js set `NEXT_PUBLIC_KELLO_SERVICE_URL`; for Start set `VITE_KELLO_SERVICE_URL`. Use the deployed service URL before building:

```sh
bun run build
bun run start
```

Open `/` or `/client` for the browser client. Both connect directly to the deployed Neon Function for authentication and RPC, and to Neon Realtime for live queries. The frontend does not host auth, session, or RPC handlers. `kello dev` watches the cloud backend; each framework’s frontend dev server serves its UI.

Before using managed Neon browser login, review the [hosted cookie-delivery limitation](/authoring/auth#custom-better-auth-sessions-and-jwts).

## Create or integrate your own project

Use `kello init <directory> --name <name>` to scaffold source locally, or `kello integrate` to preview additions to an existing frontend and `kello integrate --apply` to write them. These commands do not silently overwrite existing files. Install/link the local Kello package while no public release is available. Use `kello create <directory> --name <name> --region <region>` only when you intend to create provider resources.

Read [project configuration](/authoring/configuration) for the file layout and [CLI commands](/reference/cli) for operational options.

## Check that setup worked

| Check                                  | Expected result                               | If it fails                                                 |
| -------------------------------------- | --------------------------------------------- | ----------------------------------------------------------- |
| `kello doctor --json`                  | The intended project loads with its contracts | Check the working directory, link, and configuration        |
| `kello generate`                       | New methods appear in `_generated/api`        | Match contract files to default-exported routers            |
| `kello deploy --dry-run --json`        | A reviewable plan for the intended branch     | Check credentials, drift, and migration review requirements |
| Authenticated browser call             | Private data belongs to the signed-in user    | Check token trust and server authorization                  |
| A write while a second view subscribes | The subscribed view receives a new snapshot   | Check worker/runtime logs and live-query configuration      |

For a local Next or Start frontend, run `bun run dev:backend` in one terminal and `bun run dev` in another from that example directory. Set the frontend's public Kello URL to the backend address printed by `kello dev`, then restart the frontend. Vite examples use their own `dev:frontend` script; inspect the selected example's `package.json` instead of assuming all scripts match.
